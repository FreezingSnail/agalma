B1.7 — execution/kernel extraction evidence

Bead: agalma-0ht.8. Design: docs/b1-extraction.md (D1–D5, D7; execution boundary note under "Risks / open items"). Depends on agalma-0ht.7 (B1.6 ledger extraction). HEAD at start: adf21d0.

Goal: move the ExecutionApi boundary behind a process (Unix-socket) boundary without changing any contract schema or consumer logic, and prove replacement through the declared API with dual-binding parity, a staged rebind with an in-flight pinned operation, rollback, and IPC conformance.

Boundary resolution (done first)

The design record flagged: "KernelEngine does not implement ExecutionApi today (only Executor<L> does); B1.7 must resolve the actual replaceable boundary before extraction." Resolution:

  • The conductor's current execution service is the M1 seed Executor<L> (crates/agalma-execution/src/executor.rs). It hosts Vec<(ExecutionPhase, Box<dyn Activity>)> — activity closures built from conductor code. Those closures cannot cross a process boundary without re-architecting phases, so moving the seed executor out is out of scope.
  • The replaceable boundary with real pressure is the B0 durable kernel: KernelEngine<L: LedgerApi> (crates/agalma-kernel/src/engine.rs) is pure data-in/data-out over LedgerApi (apply / pending_dispatch / receipt / timers / directives / leases) with a Box<dyn SandboxApi + Send> seam (with_sandbox). It is the candidate replacement for the seed executor and is process-ready in shape.
  • B1.7 therefore extracts ExecutionApi for the kernel candidate: a server bin hosting KernelEngine<LedgerClient> (+ SandboxClient seam) and an ExecutionClient implementing ExecutionApi.
  • Default conductor execution remains the seed executor in-process. The kernel process binding is candidate-only: selectable (AGALMA_EXECUTION_TRANSPORT=process) and exercised by tests; the production path is unchanged.

Faithfulness and gaps (ExecutionApi → kernel)

The kernel separates the pure transition (KernelEngine::apply) from the external effect dispatch (run_activity/recover_pending, which call a registered ActivityHandler). Handlers are consumer-built Rust closures that cannot be hosted generically behind the boundary, so:

ExecutionApi methodMappingResult
start(task)derive next free ExecutionId::derive(task, n); apply(Command::Start)faithful
cancel(exec)KernelEngine::cancel (Command::Cancel)faithful
status(exec)project KernelEngine::load + pending_dispatch onto ExecutionStatusfaithful
step(exec)needs effect dispatch through a handler registryUnsupportedCapability (bare adapter) / faithful via handler-registry protocol (B1-F1)
recover()needs handler-driven effect reconciliationUnsupportedCapability (bare adapter) / faithful via handler-registry protocol (B1-F1)

Flattened cases (dispatch/recovery) are covered at the engine-op level through ExecutionOps (the same shape as the LedgerOps/TaskQueueOps precedent), and the adapter gap is asserted directly (execution_api_adapter_reports_unsupported_capability). B1-F1 (agalma-5de) closes the gap for callers that attach a handler registry (see below); the bare KernelEngine adapter still reports UnsupportedCapability because it hosts no handlers.

Default transport decision

ExecutionTransport::from_env() reads AGALMA_EXECUTION_TRANSPORT (in-process default, process optional). The production default remains the seed executor in-process; nothing in composition.rs/work.rs/lib.rs is switched to the kernel. execution_process.rs only exposes the supervised kernel candidate so a caller/test can select and drive it. This matches the bead's "Do NOT switch the production default".

Deviations and design corrections (noted, not applied to docs/b1-extraction.md)

  1. ExecutionOps carries the kernel engine surface. The frozen ExecutionApi cannot express effect dispatch/recovery without a handler registry, so the wire surface is ExecutionApi plus the kernel engine operations, unified by ExecutionOps (mirrors LedgerOps/TaskQueueOps). No contract schema changed.
  2. The engine surface is JSON for kernel-native payloads. agalma-ipc is infrastructure and holds ExecutionOps; it must not depend on agalma-kernel (that edge would cycle once the kernel server depends on agalma-ipc). Kernel-native payloads (Command/Inputs/ApplyOutcome/ KernelState/TimerFire/Reclaim) therefore cross as JSON Values, and KernelEngine<L> implements ExecutionOps by encoding/decoding them. Contract types (DispatchIntent, OperationReceipt, TimerRecord, StateSnapshot) stay typed.
  3. with_sandbox now takes Box<dyn SandboxApi + Send> (and sandbox_mut returns &mut (dyn SandboxApi + Send)). The server host requires the engine to be Send (Handler: Send + Sync); the non-Send boxed seam prevented that. The FakeSandbox and SandboxClient implementations are Send, so existing callers compile unchanged.
  4. Serde derives added to kernel state types (KernelState, OperationRecord, DirectiveRecord, ApplyOutcome, TimerFire, Reclaim) so the engine surface can cross the boundary. No behavior change.
  5. Snapshot transfer by file (D3). export_snapshot_to/import_snapshot_from write/read the canonical JSON snapshot at a caller-supplied path under the run state dir; only the path crosses the frame. The kernel's own LedgerClient continues to use the ledger boundary's snapshot file transfer internally.
  6. ExecutionApi::start does not begin a lease. The kernel ties leases to explicit begin_lease (an ExecutionOps op), not to Start; the returned execution id still matches the seed's ExecutionId::derive(task, generation).
  7. Kernel Start coarsens to Pending. Start sets ExecState::Ready, which the coarse projection maps to ExecutionState::Pending; a status immediately after start reports phase=Intake state=Pending (the seed reports Running). This is the kernel's own coarse projection, not a boundary artifact.
  8. No single-writer lock on the kernel server. The durable state owner is the ledger server (which keeps its own lock); the kernel server is stateless apart from its ledger connection and binds a unique socket per state dir.
  9. Cargo.lock. Modified only for the two new intra-workspace dependency edges (agalma-kernel -> agalma-ipc, agalma-conductor -> agalma-kernel). No external crate was added.
  10. Unix socket path length. Sockets live directly under the run state dir (ledger.sock, execution.sock) to stay within SUN_LEN (~104 bytes). Tests use short target/test-runs/ep-<pid>-<n>/ run dirs.

B1-F1 — handler-registry protocol (agalma-5de)

B1.7 left ExecutionApi::step/recover returning UnsupportedCapability because the kernel separates the pure transition from handler-driven effect dispatch and handlers are consumer-built Rust closures that cannot cross a process boundary. B1-F1 defines the handler-registry protocol: the engine (durable owner) begins an operation and hands the caller a serializable EffectContext; the caller performs the effect through a caller-hosted EffectDispatch registry; the engine completes the operation from a serializable EffectReport. Only the nondeterministic effect half crosses the boundary — exactly the split the kernel already draws between transition and handler — while every durable step (duplicate/conflict/park/block checks, the announce-before-effect commit, and the completion receipt) stays server-side.

The protocol is transport-agnostic: KernelEngine<L> implements the same three operations in-process (begin_step / begin_pending_step / complete_step), so an in-process binding and a process binding expose one surface.

New interfaces

  • agalma_ipc::execution_handler: HandlerKey (name@version), EffectMode (Dispatch/Reconcile), EffectContext, EffectProbe (Present/Absent/Ambiguous), HandlerError, EffectReport (Present/Executed/Ambiguous/KnownFailure/UnknownOutcome), EffectDispatch (caller-hosted registry), StepBegin (Effect/Done).
  • agalma_ipc::ExecutionOps additions: begin_step (explicit OperationRequest), begin_pending_step (the durable pending operation), complete_step. Params PendingStepCall/BeginStepCall/CompleteStepCall. EXECUTION_METHODS grows 18 → 21.
  • agalma_ipc::ExecutionClient: with_effect_dispatch / has_effect_dispatch. With a registry attached, ExecutionApi::step/recover drive the protocol; without one they forward to the server adapter and keep reporting UnsupportedCapability (the bare-engine gap).
  • agalma_kernel::activity: begin_activity / finish_activity split run_activity into the durable begin (announce) and the commit (complete/park); EffectMode, ActivityBegin, BeginOutcome, EffectReply. run_activity itself is unchanged.

Semantics

  • recover mirrors recover_pending: reconcile each durable pending intent; Present completes it (reconciled), Absent leaves it pending, Ambiguous parks; a park/block halts further recovery for that execution.
  • step drives the single pending operation of the execution; with no pending intent it projects Idle/Parked from status. begin_step additionally supports fresh dispatch: the intent is durable before the effect runs.
  • Handler errors propagate faithfully (KnownFailure/UnknownOutcome), exactly as run_activity does.

IPCX.7 — execution/kernel boundary on Connect (agalma-ebg.8)

Status: green. Design docs/ipc-connect-design.md (D1–D7, D7 boundary #6). Pattern: agalma-ebg.4 (sandbox, dd18375) / agalma-ebg.7 (ledger, 062a9b4). The largest boundary now speaks the Connect transport; the frozen ExecutionApi contract, the envelope semantics, the caller-side effect-dispatch protocol (agalma-5de/B1-F1), and the snapshot-file transfer are unchanged.

What changed

The typed ExecutionApi/ExecutionOps client and the kernel server moved onto the per-boundary wire selector (agalma_ipc::{Wire, WIRE_ENV}, reused from agalma-ipc::connect). The execution/kernel process wire defaults to Connect; AGALMA_IPC_WIRE=framed restores framed for parity runs. The kernel server's own LedgerClient connection uses the same wire, so the nested kernel→ledger edge speaks the transport the supervisor selected for this boundary.

Nesting fix (scope note)

The kernel server is the first component that both serves over Connect and talks to a peer over Connect: its LedgerClient is called synchronously from inside the async Connect handler. The framed client is synchronous, so this was latent; on Connect the client's blocking call (Runtime::block_on) would panic ("cannot start a runtime from within a runtime"). block_on_nested steps the worker aside with tokio::task::block_in_place so the peer runtime's reactor progresses. This is a one-file ledger_client change (the boundary the kernel hosts, not a schema/behaviour change); the same latent hazard is fixed defensively in the execution client. The other Connect clients are not nested today and were left untouched.
