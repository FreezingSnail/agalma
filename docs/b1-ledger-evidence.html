B1.6 — ledger extraction evidence

Bead: agalma-0ht.7. Design: docs/b1-extraction.md (D1–D5, D7, D3 snapshot-file rule). Depends on agalma-0ht.6 (B1.5 task-queue extraction). HEAD at start: 53ebe0c.

Goal: move the durable-state component (LedgerApi) behind a process (Unix-socket) boundary without changing any contract schema or executor/kernel logic, and prove replacement through the declared API with dual-binding parity, a quiesced export/import rebind, rollback, and IPC conformance. This is the durable-state boundary: the server owns the database, enforces a single writer per state generation, and transfers snapshots as files (never frames).

Why LedgerOps, not just LedgerApi

The frozen LedgerApi carries export_state/import_state as in-memory StateSnapshot values. The durable-state snapshot can exceed the 16 MiB frame cap, so D3 requires snapshot transfer via files under the run state dir, not frames. LedgerOps: LedgerApi adds the path-based primitives the server hosts (export_snapshot_to/import_snapshot_from); LedgerClient implements the trait export_state/import_state over them (server writes/reads the file, the client transfers only the path and reads/parses the file locally on the same host). agalma-ledger implements LedgerOps for SqliteLedger; the conductor's LedgerHandle implements it by delegation. This is an internal helper trait in infrastructure; no contract schema changed.

Default transport decision

LedgerTransport::from_env() reads AGALMA_LEDGER_TRANSPORT (in-process default, process optional). The default remains in-process, matching B1.2–B1.5. The construction sites now consult the transport factory: Composition::build and work::work build the executor's ledger through LedgerHandle::from_transport(&state_dir, LedgerTransport::from_env()). With the default the run/work path is behaviourally unchanged; with AGALMA_LEDGER_TRANSPORT=process the sites spawn the supervised ledger server (socket <state_dir>/ledger.sock, owning <state_dir>/ledger.sqlite) and bind a LedgerClient. The kernel/executor construction (Executor<L: LedgerApi>) is unchanged: it now receives Executor<LedgerHandle> at the conductor seam only.

Single-writer rule (D3)

The ledger server is the single writer for one state generation. On start it acquires <state_dir>/ledger-server.lock (pid written to the file); a second server for the same state dir refuses to start while a live pid holds the lock, and reclaims a stale lock (dead pid). The lock is released on process exit (killed) or removed on clean return. The rule: at most one ledger server (one writer) owns a state dir at a time; export_state/import_state run only while quiesced, and rebinding moves a snapshot file between servers rather than sharing a database.

Snapshot file transfer (D3)

export_snapshot_to/import_state_from write/read the canonical JSON snapshot (StateSnapshot::to_canonical_json) at a caller-supplied path under the run state dir. Only the path crosses the wire; the snapshot payload never becomes a frame. LedgerApi::export_state/import_state on LedgerClient are thin wrappers: the server writes/reads the file, the client reads/writes it locally on the same host and (de)serializes.

Deviations and design corrections (noted, not applied to docs/b1-extraction.md)

  1. LedgerOps carries the snapshot file primitives. The design names LedgerClient as implementing "the same contract trait"; D3 requires snapshot transfer by file, so the wire surface is the frozen LedgerApi plus export_snapshot_to/import_snapshot_from, unified by LedgerOps. No contract schema changed.
  2. The handle is cloneable and shared. Unlike the stateless component handles, LedgerHandle is Clone over an Rc-shared backend so every per-task executor in a work loop uses one durable-state owner (single writer per state generation). The supervised server lives until the last clone drops.
  3. reconcile.rs generalized over LedgerApi. reconcile_projection and its helpers now take &L where L: LedgerApi + ?Sized instead of &SqliteLedger, so the same call accepts either the in-process ledger or the transport handle. The comparison/rewrite logic is unchanged (the call bodies are byte-for-byte the same methods).
  4. Auxiliary direct connections remain (accepted deviation; B1-F2 agalma-1o3). The executor's ledger — the extracted boundary — is bound through LedgerHandle. A few short-lived conductor helpers (digest::record, provider_auth::record_audit, routing::resolve_route's decider, the phases.rs activity event writers, and the read-only status/digest/reconcile/resume CLI subcommands) still open their own SqliteLedger connection for a single operation. Under process transport these are secondary SQLite (WAL) connections to the same file; the durable-state owner and the export/import generation are still the server (guarded by the lock), and the rebind test quiesces the conductor before exporting.

B1-F2 revisited this and converged what is reachable, with the remainder accepted deliberately because routing them through the boundary is impossible without a redesign that is out of this task's scope:

  • Why a fresh process connection cannot be used. The ledger server serves one connection at a time — Server::accept_loop accepts a connection and runs serve_connection to completion (until the peer disconnects) before it returns to accept. The conductor's bound LedgerHandle holds its client connection open for the whole run, so any auxiliary helper that opened its own LedgerClient would queue in the listener backlog and block forever. This is pinned by tests/ledger_process.rs::second_connection_is_not_served_while_the_primary_is_held.
  • Why the shared handle is not reachable. The only correct route is to reuse the same LedgerHandle (shared Rc backend, single connection). That handle is owned by the executor (work.rs) and by the activity set (phases.rs), neither of which passes it to the auxiliary helpers: the Activity trait (agalma_execution) receives only the OperationContext, and threading the handle through the executor/activity seam, the activities(...) constructor, and the work.rs call sites is a kernel/execution + work.rs change outside this bead's file scope.
  • Why the read-only CLI subcommands stay direct. They run as standalone processes; under process transport the conductor (and its ledger-server lock) is usually live, so spawning a server fails and a client connection would deadlock. A WAL read is the correct, non-blocking access there.
  • Converged in B1-F2. provider_auth::record_audit_via takes a bound ledger (no state-dir argument, so it structurally cannot open a secondary connection) and the in-scope Composition::build call site now passes its already-bound LedgerHandle. The record_audit(state_dir, …) wrapper is retained only for the off-limits work.rs call site. A bound-handle routing proof lives in provider_auth::tests::record_audit_via_routes_through_the_bound_ledger.

Net: one fewer secondary connection on the M0 (run) path; the work-loop and CLI accesses remain documented, secondary WAL reads/writes with the accepted rationale above. The goal here is single-writer clarity (each access is now either on the handle or explicitly named here), not correctness today.

  1. LedgerApi has no Describe/binding record. As for the sandbox/workspace/ task-queue boundaries, the "staged rebind" is a supervised-server swap with the in-flight pinned dispatch intent preserved across a snapshot export/import, rather than a BindingRecord swap (the harness boundary keeps the record-based rebind).
  2. The server takes --socket <path> and --state-dir <path>. The ledger backend is rooted at a state dir (DB + snapshot files + lock), so the server takes both; run_from_args parses them.
  3. No Tokio runtime in the ledger server. The backend is rusqlite (synchronous), so the serial serve loop runs synchronously (mirroring the reference harness, workspace, and task-queue servers).
  4. Unix socket path length. The ledger socket lives directly under the run state dir (ledger.sock) to stay within SUN_LEN (~104 bytes). Tests use short target/test-runs/lp-<pid>-<n>/ run dirs.
  5. Cargo.lock. Modified only for the new intra-workspace dependency edge (agalma-ledger -> agalma-ipc). No external crate was added.

Consumer-invariance proof

B1-F2 — auxiliary ledger connections (agalma-1o3)

Follow-up to deviation 4. Scope: crates/agalma-conductor only (digest.rs, provider_auth.rs, routing.rs, phases.rs, ledger_process.rs, minimal lib.rs wiring, co-located tests). The work loop (work.rs), the read-only TUI (watch.rs, status.rs), and the review/sandbox modules are owned by other workers and were not touched.

Converged

  • provider_auth::record_audit_via(ledger: &mut dyn LedgerApi, audit) — the audit writer now takes the bound ledger and has no state-dir argument, so it cannot open a secondary connection. record_audit(state_dir, …) remains as a thin wrapper for callers that do not hold the handle.
  • Composition::build (composition.rs) passes its already-bound LedgerHandle to record_audit_via, so the M0 run path records the provider-auth audit on the conductor's single ledger connection. In-process behaviour is unchanged (same backend, one fewer connection); under process transport the audit no longer opens a second SQLite connection to the server's database.

Documented deviation (rationale in deviation 4 above)

  • digest::record (caller: work.rs), routing::resolve_route's decider (callers: work.rs, review.rs, sweep.rs, concierge.rs), the phases.rs activity event writers, and the read-only digest/reconcile/resume CLI subcommands keep direct secondary WAL connections. Routing them through the boundary needs the shared LedgerHandle, which is not threaded to these helpers, and a fresh process connection would deadlock against the serial ledger server. Both facts are structural; removing them is a redesign (executor/activity seam + work.rs + CLI), out of scope here.

  • tests/ledger_process.rs::second_connection_is_not_served_while_the_primary_is_held — pins the serial single-connection server behaviour that makes a fresh-connection route impossible (the deviation rationale).
