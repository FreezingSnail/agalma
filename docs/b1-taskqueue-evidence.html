Bead: agalma-0ht.6. Design: docs/b1-extraction.md (D1–D5, D7). Depends on agalma-0ht.5 (B1.4 workspace extraction). HEAD at start: 78ab8e6.

Why TaskQueueOps, not just TaskQueueApi

The conductor drives more than the frozen six-method TaskQueueApi: the ledger-vs-projection reconcile (reconcile.rs) calls the adapter's projection/set_status/remove_label. To keep work/reconcile logic unchanged (D5) while carrying those operations across the boundary, agalma-ipc defines TaskQueueOps: TaskQueueApi holding the full surface. agalma-taskqueue implements it for the bd-backed BdTaskQueue; TaskQueueClient and the conductor's TaskQueueHandle implement it over the transport (the handle delegates to whichever backend is bound). This is an internal helper trait in infrastructure; no contract schema changed. IssueProjection (previously private to agalma-taskqueue) is now the wire DTO in agalma-ipc, re-exported from agalma-taskqueue so existing paths keep resolving.

Default transport decision

TaskQueueTransport::from_env() reads AGALMA_TASKQUEUE_TRANSPORT (in-process default, process optional). The default remains in-process, matching B1.2–B1.4. The construction sites now consult the transport factory: work::work and reconcile_command build the queue through TaskQueueHandle::from_transport(&state_dir, &repo, TaskQueueTransport::from_env()). With the default the work/reconcile path is behaviourally unchanged; with AGALMA_TASKQUEUE_TRANSPORT=process the sites spawn the supervised task-queue server (socket <state_dir>/taskqueue.sock, serving <repo>/.beads) and bind a TaskQueueClient.

Conductor task-queue supervision

TaskQueueProcess spawns agalma-taskqueue-server --socket <state_dir>/taskqueue.sock --repo <repo> as a process-group leader, waits for READY, and connects TaskQueueClients. It reuses the exact spawn_supervised/stop_supervised helpers shared with the harness/sandbox/workspace boundaries (one supervision implementation for every boundary). The server targets the same <repo>/.beads store the in-process backend used, so claims and projections are identical across bindings.

TaskQueueHandle holds either the in-process BdTaskQueue or a TaskQueueClient plus the Rc<TaskQueueProcess> that keeps the server alive for the handle's lifetime (stopped on drop). It exposes the full surface by delegation, so the work/reconcile call bodies are unchanged — only the constructed type differs.

Deviations and design corrections (noted, not applied to docs/b1-extraction.md)

  1. TaskQueueOps carries the reconcile projection surface. The design names TaskQueueClient as implementing "the same contract trait"; the conductor's reconcile also drives projection/set_status/remove_label, so the wire surface is the frozen TaskQueueApi plus those operations, unified by TaskQueueOps. No contract schema changed.
  2. IssueProjection moved to agalma-ipc. The projection type was private to agalma-taskqueue; the transport needs one shared wire representation, so it now lives in infrastructure (agalma-ipc) with has_label/has_comment, and agalma-taskqueue re-exports it. agalma-ipc does not depend on any implementation crate.
  3. TaskQueue has no Describe/binding record. TaskQueueApi has no Describe, so (as for the sandbox/workspace boundaries) the "staged rebind" is a supervised-server swap with the in-flight claim pinned to its claiming server (the bd store on disk is the durable artifact), rather than a BindingRecord swap (the harness boundary keeps the record-based rebind).
  4. The server takes --repo <path> (and optional --bd/AGALMA_TASKQUEUE_BD). Unlike the socket-only sandbox/harness servers, the bd backend is rooted at a repository, so the server takes --repo; run_from_args parses --socket, --repo, and an optional bd executable override.
  5. No Tokio runtime in the task-queue server. The backend shells out to bd via std::process, so the serial serve loop runs synchronously (mirroring the reference harness and workspace servers, not the Tokio-based sandbox/OpenCode servers).
  6. Unix socket path length. The task-queue socket lives directly under the run state dir (taskqueue.sock) to stay within SUN_LEN (~104 bytes). Tests use short target/test-runs/tq-<pid>-<n>/ run dirs.
  7. Cargo.lock. Modified only for the new intra-workspace dependency edge (agalma-taskqueue -> agalma-ipc). No external crate was added.

Consumer-invariance proof

crates/agalma-conductor/src/work.rs changes are limited to the import and the queue type (BdTaskQueue → TaskQueueHandle) at four function parameters and one construction site; every intake/claim/comment/close/label call, phase dispatch, ordering, recovery, and activity body is unchanged. lib.rs and reconcile.rs changes are limited to the queue construction/parameter type (TaskQueueHandle) and the projection type (agalma_ipc::IssueProjection); reconcile_projection compares exactly the same fields. The conductor tests fencing.rs/watchdog.rs that construct a queue were updated to construct the handle (TaskQueueHandle::in_process).
