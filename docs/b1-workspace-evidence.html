B1.4 — workspace extraction evidence

Bead: agalma-0ht.5. Design: docs/b1-extraction.md (D1–D5, D7). Depends on agalma-0ht.4 (B1.3 sandbox extraction). HEAD at start: 127f49f.

Goal: move WorkspaceApi (plus the M1 repo-mode operations the conductor drives) behind a process (Unix-socket) boundary without changing any contract schema or consumer (phase) logic, and prove replacement through the declared API with dual-binding parity, staged rebind, rollback, and IPC conformance.

Why WorkspaceOps, not just WorkspaceApi

The conductor drives more than the frozen six-method WorkspaceApi: the verify and integrate phases call the M1 repo-mode operations (prepare_repo/commit_candidate/prepare_verify_checkout/origin_receipt/ integrate_origin/integrated_receipt/revert_origin/candidate_sha). To keep phase/work logic unchanged (D5) while carrying those operations across the boundary, agalma-ipc defines WorkspaceOps: WorkspaceApi holding the full surface. agalma-workspace implements it for the git-backed Workspace; WorkspaceClient and the conductor's WorkspaceHandle implement it over the transport (the handle delegates to whichever backend is bound). This is an internal helper trait in infrastructure; no contract schema changed.

Default transport decision

WorkspaceTransport::from_env() reads AGALMA_WORKSPACE_TRANSPORT (in-process default, process optional). The default remains in-process, matching B1.2/B1.3. The construction sites now consult the transport factory: Composition::build and work::build_executor build the workspace through WorkspaceHandle::from_transport(&state_dir, WorkspaceTransport::from_env()). With the default the phase path is behaviourally unchanged; with AGALMA_WORKSPACE_TRANSPORT=process the sites spawn the supervised workspace server (rooted at the run state dir, socket <state_dir>/workspace.sock) and bind a WorkspaceClient.

Conductor workspace supervision

WorkspaceProcess spawns agalma-workspace-server --socket <state_dir>/workspace.sock --base-dir <state_dir> as a process-group leader, waits for READY, and connects WorkspaceClients. It reuses the exact spawn_supervised/stop_supervised helpers shared with the harness/sandbox boundaries (one supervision implementation for every boundary). The server is rooted at the same base dir the in-process backend used, so <base_dir>/runs/<exec> checkout paths are identical across bindings.

WorkspaceHandle holds either the in-process Workspace or a WorkspaceClient plus the Rc<WorkspaceProcess> that keeps the server alive for the handle's lifetime (stopped on drop). It exposes the full surface by delegation, so the phase/work call bodies are unchanged — only the constructed type differs.

Deviations and design corrections (noted, not applied to docs/b1-extraction.md)

  1. WorkspaceOps carries the M1 repo-mode surface. The design names WorkspaceClient as implementing "the same contract trait"; the conductor also drives the M1 repo-mode operations, so the wire surface is the frozen WorkspaceApi plus those operations, unified by WorkspaceOps. No contract schema changed.
  2. Workspace has no Describe/binding record. WorkspaceApi has no Describe, so (as for the sandbox boundary) the "staged rebind" is a supervised-server swap with the in-flight checkout pinned to its preparing server, rather than a BindingRecord swap (the harness boundary keeps the record-based rebind).
  3. The workspace server needs a base dir. Unlike the sandbox/harness servers (socket only), the git backend is rooted at a directory, so the server takes --base-dir <path>; run_from_args parses both --socket and --base-dir.
  4. No Tokio runtime in the workspace server. The backend shells out to git via std::process, so the serial serve loop runs synchronously (mirroring the reference harness server, not the Tokio-based sandbox/OpenCode servers).
  5. Unix socket path length. The workspace socket lives directly under the run state dir (workspace.sock) to stay within SUN_LEN (~104 bytes). Tests use short target/test-runs/wp-<pid>-<n>/ run dirs.
  6. Cargo.lock. Modified only for the new intra-workspace dependency edge (agalma-workspace -> agalma-ipc). No external crate was added.

IPCX.4 — workspace boundary on the Connect transport

Bead: agalma-ebg.5. Design: docs/ipc-connect-design.md (D1–D7). Foundation: agalma-ebg.2 (ipc.proto, Connect stack + pins, UDS accept loop, client core, Connect-level conformance harness). Depends on agalma-ebg.4 (IPCX.3 sandbox boundary, the migration pattern). HEAD at start: 4628801.

Goal: move the already-extracted WorkspaceApi (+ the WorkspaceOps repo-mode surface) process boundary onto the Connect transport (IPCX D7, boundary #3) without changing the envelope semantics or any consumer logic, and prove it with the B1 recipe — dual-binding parity, staged rebind, rollback, IPC conformance — extended to the Connect wire. As in IPCX.2/IPCX.3, the per-boundary evidence named by D4 (docs/ipcx-<boundary>-evidence.md) is folded into this file so the workspace boundary's B1 and IPCX evidence stay together.

The selected wire is exported to the child in the same variable, so the server serves the matching transport. Both wires announce the identical READY {json} line, so the supervisor handshake is unchanged; WorkspaceApi is Describe-free, so there is no binding gate to keep wire-agnostic.
  • Envelope semantics are preserved verbatim on both wires: v/id/method/ params_json; duplicate-id receipt replay; UnknownOutcome/contract errors in-band; version refusal; unknown-method UnsupportedCapability. The Connect path reuses Server::dispatch, so no envelope code was forked.
  • WorkspaceOps (the frozen WorkspaceApi plus the M1 repo-mode operations) is unchanged; only the transport beneath it differs.
  • No new dependency. connectrpc/buffa stay confined to agalma-ipc (architecture test green); no Cargo.toml/Cargo.lock change.

Deviations and notes

  1. The IPCX design D4 names a per-boundary docs/ipcx-<boundary>-evidence.md; this bead's scope extends the existing B1 workspace evidence instead, keeping the framed and Connect proofs side by side (matching IPCX.2/IPCX.3).
  2. The workspace process wire defaults to Connect. WorkspaceApi is Describe-free, so the "staged rebind" remains a supervised-server swap with the in-flight checkout pinned to its preparing server (B1.4 note 2), now over the Connect wire.
  3. WorkspaceProcess::spawn/spawn_with_spec keep their signatures (defaulting to workspace_wire()); spawn_with_spec_wire is the explicit-wire entry point the parity test uses. The re-exec'd child serves the env-selected wire because spawn_with_spec_wire exports AGALMA_IPC_WIRE to it.
  4. serve_wire installs a multithread Tokio runtime for both wires. The git backend still shells out through std::process and needs no reactor itself, but the Connect accept loop does, so (unlike B1.4) the server now hosts one.
  5. The Connect accept loop logs peer resets (connect connection error) at most; the workspace scenario's heavier disconnect/stopping sequence surfaces these benign lines in test output without affecting the transcripts.
