Sequencing and release

The shared first-tranche design gate is agalma-fjq; its design receipt records schemas, examples, failure/compatibility semantics, ownership and decomposition checks. Closing that design gate does not release implementation tasks. At that design audit, all 61 planned children were staged/deferred. Subsequent explicit operator releases and implementation reviews are recorded in bd and the batch handoff; this planning snapshot does not override their current status. Later MX/CV/M3/P1 work also blocks on agalma-16k, which freezes those seams against actual HP/SM runtime evidence. See standup beads and later roadmap beads for exact IDs/dependencies.

  1. SF builds reliable immutable task delivery, execution-scoped recovery, cancellation, stop/scope enforcement, request liability reservations and independently selected builder/planner/reviewer routes. SF.9 and SF.10 prove self-build and the fresh full pipeline under bootstrap oversight.
  2. HP supplies independent packages, discovery, registry/supervision, common IPC, ledger namespaces, declarative UI and durable actions. Its exit installs an unfamiliar plugin without rebuilding the hub.
  3. SM proposes and directive-authorizes prompt/skill tasks, compares immutable baseline/candidate on protected paired trials, qualifies success gains with regression/economic limits, canaries and retains or rolls back an improvement. Screening never substitutes for qualification. Plugins follow an allowlist.
  4. MX completes remaining M2 obligations; CV migrates actual consumers onto the common platform. M2 cannot close solely because its first SM children close.
  5. M3 extends release policy with cadence, durable scheduling, aggregate cash/quota/local limits, supervision, complete backups, restore/fault drills and genuine 72-hour evidence. Display-only or post-spend budget checks do not satisfy admission enforcement.
  6. P1 adds reproducible immutable core candidates, an external recovery owner, isolated shadow/canary, fenced drain/activation and automatic compatible rollback. Initial autonomous core updates preserve the ledger schema. Binary rollback never rewinds the live database. Enable code autonomy only after the original protected acceptance/evaluator, budget, reconciliation and rollback requirements have independent evidence.

Live provider prices/request limits are not certified by this planning session. Unsupported profiles deny paid dispatch until SF.7 records reviewed evidence. Future test names in beads are implementation deliverables, not current passing tests. This session neither releases tasks nor performs paid inference.
