Remaining self-mutation roadmap, revision 1

Date: 2026-10-12. This follows the first SF -> HP -> SM standup and the exact contracts in self-mutation-contracts.md. It turns the remaining planning areas into bounded implementation tranches. Future implementation remains staged; the runtime design gate rechecks these plans against actual SF/HP/SM evidence before release. Planned test paths below do not claim existing tests or passing results.

Sequence and milestone accounting

  1. Finish the shared design gate and first reliable self-build/plugin/measured-win tranche, including SM.9's directive-authorized prompt/skill release and SF.10's fresh full pipeline proof and SF.11's prerequisite-aware review admission. Bootstrap code retains transitional human oversight.
  2. Migrate existing production services onto the common platform. Build the remaining M2 capabilities as independently scoped plugins/adapters.
  3. M3: operate the bounded factory unattended and prove 72-hour recovery/restore.
  4. P1: prove controlled replacement and code self-correction, then enable an explicitly versioned code-autonomy policy.

M2's first measured-mutation tranche is not the whole milestone. The extensions tranche is part of the original nerve/onboarding/memory/decider obligations. The M3 exit depends on both measured mutation and those extensions, plus production service convergence. P1 depends on M3. Reporting visibility never substitutes for an admitted workflow capability or production dispatch evidence.

Keep vendor hooks in the harness adapter. A nerve bridge emits canonical events and bounded requests; it cannot own durable state, authorization or spending. Prompt/skill curation and new model/decider activation use the existing SM gate.

M3: always-on operations

The hub owns scheduling and authority. Scheduler policy is canonical immutable data; observation/mining plugins can propose tasks but cannot silently dispatch them. A single durable operator lease owns admissions. Serial dispatch remains the baseline; no hedged calls, parallel builders or distributed scheduler.

Initial cadence: ready-work scan every 5 seconds when idle; reconciliation every 30 seconds; mining every 15 minutes; digest every 24 hours. Persist the next due time and last receipt for each job. Coalesce missed ticks after restart into one reconciliation, not a burst of historical work. Empty/blocked queues sleep until the next tick or state notification. Failures use capped exponential backoff.

Extend the SM.9 release service instead of creating another approval mechanism. Release policy checks active directive, target/class allowlist, decomposition approval, complete immutable inputs, closed blockers, scope/protected constraints, role eligibility and remaining directive/task budgets. It records the exact decision and reason before changing the queue projection. Projection is reconcilable; a cleared defer date, a validator decomp-approved label, or a resolved bootstrap human gate alone is not trusted automation authority. Bootstrap Rust and arbitrary executable plugins remain under their existing gates (the native human execution-approval gate for staged children).

Aggregate caps use a hierarchy: platform -> active directive -> task/evaluation scope -> provider request. A reservation consumes all applicable caps in one admission decision; no race between unrelated scopes. Cash windows track incurred charges and outstanding liability across resets; quota windows use reviewed provider observations. Unknown usage does not disappear at midnight. Local inference records CPU time, memory ceiling and wall deadline even with zero cash.

Backups are hub-triggered through public APIs, with a consistency watermark and artifact inventory. A restore stops dispatch, uses an isolated destination, checks receipt/external-effect agreement and increments ownership fencing before resume. Backups cannot establish that already emitted external effects vanished. Retention collects only objects unreachable from active/pinned packages, operations, candidates, rollback refs and retained backups. Low disk headroom suppresses new builds; it does not delete pinned evidence to keep running.

Live 72-hour operation needs an explicit directive with nonzero total caps and workload. Planning does not invent a dollar allowance or start that run. The deterministic drill can pass earlier, but M3 stays open until genuine operations evidence and a restore drill satisfy its original exit.

P1: core update and removal of transitional code oversight

The running candidate cannot be its sole evaluator, launcher, or rollback owner. Use a small external supervisor/bootstrap process with a stable versioned handover API, its own bounded health watchdog, and retained accepted packages. The supervisor is outside the first autonomous code-mutation scope. Changing that recovery root requires a separately versioned platform change.

An immutable CoreCandidate pins source SHA, executable/package digest, build recipe/toolchain/dependency lock, configuration, compatible contract and ledger schemas, protected suite/evaluator evidence, current accepted baseline and directive. Reproducibility means either identical binary digests or a documented deterministic normalization with exact residual differences; compile success is not the claim. Build and verify in isolated state before touching the live factory.

State compatibility and binary compatibility are separate. A binary rollback requires a writer compatible with the current ledger schema; a pre-upgrade DB restore is an operations recovery with external-effect reconciliation. Initially, automatic core updates are schema-preserving. A schema-changing candidate parks for the separately authorized migration procedure. This keeps a first core self-update from claiming automatic live database downgrade.

Shadow processes have read-only isolated state and no target-action credentials. Canaries begin only after M3 and the complete protected evaluation. The external supervisor owns activation/rollback operation IDs; the hub can request but cannot forge its receipt. Failed startup denies new effects before returning to the accepted runner. A paused factory remains paused across either direction.

P1's destination is automatic routine code integration under an active directive, not a permanent approval queue. Enable it only after the original protected acceptance, evaluator, paired bench, scope, budget, crash/lease/cancel, rollback and directive-bounded action requirements all have recorded evidence.

Backlog reconciliation and Router policy

Keep agalma-i5h.7 as evidence of authored/validated/staged decomposition. Its record does not prove approval -> execution -> final review -> epic closure. Use a fresh bounded standup feature for that full proof, not duplicate TUI work.

The agalma-63m audit is recorded in tui-pilot-reconciliation.md. Its ten children duplicate completed agalma-3kr behavior and are retired with individual evidence references. Missing durable cancellation, registry-driven content, public ledger convergence and fresh pipeline execution have separate SF.4, HP.6, CV.2 and SF.10 tasks. The pilot is not live factory execution evidence.

Router normalization is precise:

  • A fallback is another candidate evaluated by the same hard gates.
  • No eligible candidate, unavailable Router, unknown budget/policy, or missing reviewed billing record parks; it does not invoke an unchecked v1 table.
  • An explicit model override is recorded but still passes all hard gates.
  • A statistical quota reserve can guide ranking; provider request admission still applies the reviewed worst-case liability before any billable request.
  • The Router's process package uses common discovery/supervision/reporting, not a bespoke environment-selector/supervisor/UI path.

Apply these amendments to existing SR.5/SR.11/SR.12 task context. The original Router design may continue to describe legacy deployment/report-only budgeting; these accepted architecture and standup contracts govern new production work.

Implementation handoff

Each implementation child owns one row above, its public surface and a named behavioral integration test. Use the CP headings, rich notes, factory intake, explicit dependency edges, structural difficulty, the staged label, and a native human execution-approval gate. Cross-epic dependencies must be real bd edges even when MACHINE consumes resolves only sibling symbols. The runtime design gate must validate the actual predecessor contracts and these resource/default values before those later children release.

Use existing locked dependencies and bound APIs. Preserve concurrent edits. Sessions do not commit, rewrite acceptance/oracles, close dependencies or claim a milestone from isolated tests. Evidence children report exact bindings and remaining deviations, and distinguish scripted mechanics, live inference, and real elapsed operations. No paid run, service launch or task release occurs in this planning.
